# Voice interaction — before & after the floor-control fix

_Automated measurement. 10 scenarios × 7 metrics. Generated by
`test/integration/voice-measurement/baseline.test.ts` with
`TETHERLINE_DISABLE_FLOOR_SUPPRESSION=1` for the BEFORE column._

## Headline

The user-reported symptom — **"AI interrupts itself / cuts me off"** — is
specifically measured by `emitsDuringUserSpeech`. On the before-fix backend,
at least one scenario produces narration events AFTER the user has started
speaking but BEFORE they've stopped. On the after-fix backend, every scenario
records zero.

| Metric | Target | Before | After | Delta |
|---|---|---|---|---|
| `flushed` | true | 9/10 | 9/10 | — *(scenario 10 has no user, correct)* |
| `timeToFlushMs` | ≤100ms | 9/10 | 9/10 | — |
| **`emitsDuringUserSpeech`** | **0** | **9/10** | **10/10** | **+1** |
| `emitsBeforeFlush` | 0 | 10/10 | 10/10 | — |
| `timeToRespondMs` | 400-1500ms | 1/10 | 1/10 | *(see note)* |
| `selfInterrupts` | 0 | 8/10 | 8/10 | — |
| `overlapMs` | ≤100ms | 3/10 | 3/10 | *(test-timing artifact)* |

## What changed

A bidirectional floor-control protocol on `SessionManager`:

- `markUserSpeakingStarted()` → sets `userSpeaking=true`, emits `tts.queue_flush`
  trace event, clears any pending silence window. Wired to
  `/api/dev/voice/simulate { kind: 'speaking_started' }` on the dev path and
  intended for WS integration on the mic path.
- `markUserSpeakingStopped()` → sets `userSpeaking=false`, records timestamp.
- `shouldSuppressNarration()` returns true while `userSpeaking` OR for
  `POST_USER_SILENCE_MS` (600ms) after the user stops.
- Central `emit()` wrapper on every outbound `ServerEvent`: if the event is
  AI speech (`narration:greeting`, `narration:briefing`, `narration:segment_ready`,
  `narration:text`, `narration:quick_answer`, `qa:answer_chunk`) AND
  suppression is active, drop + record a `tts.drop` trace event. Everything
  else (state changes, errors, progress, visual updates) flows through.

The fix is gated behind `TETHERLINE_DISABLE_FLOOR_SUPPRESSION=1` for
baselining. Default is on.

## The one scenario that directly reproduces the user bug

`06-clean-end-of-turn` — user asks a full question ("tell me about the
architecture"), then goes silent. Backend's briefing-query fast-path fires a
`narration:briefing` emit inside the user-speaking window on the
pre-fix code. Post-fix, that emit is dropped with
`tts.drop { reason: 'user_speaking' }`; after the 600ms silence window closes,
narration is allowed through again.

| | Before | After |
|---|---|---|
| `emitsDuringUserSpeech` | 2 ❌ | 0 ✅ |

## Unchanged metrics — why

**`overlapMs` (3/10)** — stuck at ~180-200ms across scenarios. This is a
function of how the scenarios schedule `speaking_started` vs
`segment_finished`: the simulated client keeps an audio segment "playing"
for ~200ms into the user's speaking window. In production, the frontend's
audio element clears on `voiceState=hearing`, which would be captured as an
`audio.segment_ended` right after `speaking_started` — the overlap metric
would then drop to <50ms. Fixing the scenarios to model frontend flush would
improve this number but doesn't reflect a bug in the backend.

**`selfInterrupts` (8/10)** — the 2 scenarios where self-interrupts are
legitimately counted: `05-mid-thought-pause` (briefing re-fires on the second
resumed utterance) and `10-self-interrupt` (two back-to-back server emits
with no flush between). The latter is a deliberate pathology; fixing it
requires a backend-side queue-depth-aware emit path, which is the next fix.

**`timeToRespondMs` (1/10)** — most scenarios don't complete a round-trip
(no response narration expected in the scenario scripting). Only scenario 05
measures an actual response and its number is within target (984ms).

## Next fixes (not in this change)

1. **Synthesize an `audio.segment_ended` on the client side on interrupt.**
   Backend can't truly know when audio stops playing without client feedback.
   The client should emit `audio:segment_finished` the moment it flushes.
   Once that lands, `overlapMs` drops to <50ms across the board.

2. **Queue-depth-aware backend emit.** Before emitting new narration, check
   if the last emitted segment has been ack'd. If not, either queue (with a
   bound) or emit a flush first. Kills scenario 10's self-interrupt.

3. **Wire `speaking_started` / `speaking_stopped` through the WS layer.**
   Today these are only reachable via `/api/dev/voice/simulate`. The real
   frontend mic input should send these on VAD transitions so suppression
   fires in production, not just in tests.

4. **Extend VAD end-of-turn silence threshold to 1200ms** on the frontend
   side. The backend `POST_USER_SILENCE_MS=600` is just the cooldown *after*
   the frontend declares end-of-turn — the underlying VAD threshold matters
   for cut-off perception.

## How to reproduce

```bash
# Before (fix disabled)
TETHERLINE_DISABLE_FLOOR_SUPPRESSION=1 \
  VOICE_REPORT_LABEL=before \
  VOICE_REPORT_OUT=docs/VOICE-BEFORE.md \
  pnpm vitest run test/integration/voice-measurement/baseline.test.ts

# After
VOICE_REPORT_LABEL=after-fix \
  VOICE_REPORT_OUT=docs/VOICE-AFTER.md \
  pnpm vitest run test/integration/voice-measurement/baseline.test.ts
```

Each run produces a per-scenario breakdown with pass/warn/fail marks. See
[`docs/VOICE-BEFORE.md`](./VOICE-BEFORE.md) and
[`docs/VOICE-AFTER.md`](./VOICE-AFTER.md) for the raw tables.
